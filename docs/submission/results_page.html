SEGPILOT // measurement report · built with Paritok

We measured whether routing Paritok's compression per‑segment helps. It mostly doesn't.

Most "we optimized X" projects ship the idea and a flattering number. We shipped the idea, then measured it honestly across 7 real agent sessions and reported that it does not reliably beat Paritok's stock defaults. The lasting output is nine reproducible findings about Paritok's hosted API and a probe you can point at your own workload.

Step one · measure the instrument

Which Paritok knobs actually turn?

Before building anything, we swept every steering parameter against the hosted GPU, holding the content constant and changing one knob at a time. Two are honoured; two are silently discarded — including one the docs advertise.

query
the agent's intent — 160 → 36 tokens as it changes, and it decides which code survives
honoured
kind
what the segment is — 206 / 187 / 15 tokens for file_read / log / thinking
honoured
level
L0–L3 aggressiveness — byte-identical output, and it accepts "BANANA" with HTTP 200
ignored
target_ratio
requested ratio — byte-identical for 0.5, 0.2, "10%", null
ignored
Step two · route the knobs that work

The result, stated plainly

SEGPILOT routes query and kind per segment, so each tool result is compressed for what the agent is doing right then. Five arms isolate each layer, replayed over identical uncompressed trajectories — 3 drifted multi-bug campaigns and 4 single-bug controls.

Intent/kind routing does not reliably beat stock — even under drift.
armmust-keep retention (campaigns)
stock81%
kind_only81%
intent_only93%
segpilot93%
segpilot+guard97%

kind routing does nothing — kind_only equals stock everywhere. intent routing is weak and inconsistent — +9pp must-keep on average across three drift sessions, but it reverses on one of them, and task-relevant retention doesn't move at all.

Numbers are must-keep retention — Paritok's own training-time definition of content that must survive. It is the only axis the arms differ on; task-relevant retention saturates.

Kept in view, not hidden

Two numbers we retracted

Twice we reported an encouraging result and then had to take it back when the data was cleaned up. Both are kept — the whole project is an argument for measuring instead of trusting the first number.

"79% fewer tokens · 3.1× on a drift session"
A hand-constructed illustration, not a benchmark result. The real agent sessions did not reproduce it.
"1.61× on the drift session"
An artefact of a cache poisoned during a hosted-GPU outage — passthrough segments were cached as if compressed. Fixed, then re-run to a clean deterministic pass.
The real contribution

Nine findings about Paritok's hosted API

Each is reproducible from the repository, with a runnable check.

  1. Hosted GPU silently ignores level — and accepts "BANANA" with HTTP 200
  2. Compression cache is blind to kind/level, collapsing any per-segment policy
  3. Hosted endpoint does not validate API keys → silently unattributed usage
  4. Intent dominates compression, but stock passes one stale intent per request
  5. tag_messages/assign_level are dead code; hosted path sends kind: null
  6. Proxy hardcodes /v1, breaking Gemini / OpenRouter / Groq base URLs
  7. Documented tools/view_trace.py does not exist — so we wrote one
  8. shadow_storage: "redis" validates but is unimplemented → silent data loss
  9. The two kind classifiers disagree; the conversation-aware one mislabels every file read
Check it yourself

Reproduce every number

The reference sessions are committed, so the replay reproduces the exact figures above without recording anything new.

# which Paritok parameters actually work
python -m segpilot.probe --all

# the arms, replayed over the committed sessions
python -m segpilot.replay.harness --all --suffix __raw \
  --arms stock,kind_only,intent_only,segpilot,segpilot+guard

# regenerate the report + Pareto
python -m segpilot.replay.report --out examples/reports/
